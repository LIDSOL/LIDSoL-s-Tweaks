* 0. Introducción
Este proyecto aborda la modernización e integración de múltiples extensiones para GNOME Shell 50. El problema a resolver radica en la fragilidad de las extensiones, que dependen de APIs internas sujetas a cambios, esto genera obsolescencia: las actualizaciones del escritorio pueden /romper/ las extensiones.

Se propone usar como base el código de la extensión Aylur's Widgets (compatible hasta GNOME 44), Quick Settings Tweaks y otro puñado de extensiones con el propósito de modernizar y/o unificar estas en una única extensión compatible con GNOME Shell 50.

La arquitectura de la extensión debe facilitar su mantenimiento y se validará mediante métricas objetivas de rendimiento.

* 1. Objetivos
** Objetivos generales
Diseñar, implementar y mantener una extensión modular para GNOME que reinterprete y modernice los componentes de extensiones obsoletas como [[https://extensions.gnome.org/extension/5338/aylurs-widgets/][Aylur's Widgets]] mediante una arquitectura que facilite el mantenimiento, adaptada a los cambios de API de GNOME Shell y GJS.
- Garantizar compatibilidad toal con GNOME 50 y 51.
- Hacer los cambios necesarios para que los módulos sean estrictamente modulares.
- Separar estrictamente la lógica de negocio con la capa de presentación.
- Implementar Lazy Loading de módulos.
- Diseñar e implementar un framework modular interno. Consolidad un backend reusable y extensible.
- Diseñar un backend MPRIS unificado y extensible.
- Reducir listeners globales innecesarios y evitar memory leaks.
- Validar consumo de CPU y memoria mediante profiling.
- Optimizar el rendimiento y evitar degradación en animaciones del Shell.
- Documentar formalmente la arquitectura interna y contratos entre módulos.
- Minimizar conflictos con extensiones populares.
- Publicar la extensión.

** Decisiones de arquitectura

- **UUID sin apóstrofe** — GNOME Shell no acepta `lidsol's-widgets@lidsol`.
- **Symlink** — GNOME 50 no sigue symlinks confiablemente en runtime, pero sí para `prefs.js`.
- **prefs.js** — Navegación por categorías (Widgets, Top Bar/Panel, Shell, Quick Settings) mediante `Adw.ViewSwitcher` + `Adw.ViewStack`. Cada módulo agrega `Adw.PreferencesGroup` a la página de su categoría.
- **ModuleLoader** — Lazy loading dinámico: cada módulo tiene un `enabledKey` en GSettings. `_watchEnabledKey()` permite toggle en runtime vía `changed::` signal.
- **Aislar errores por módulo** — `_enableModule()` envuelto en try/catch para que un módulo roto no bloquee los demás.
- **Schema unificado** — Todas las keys GSettings en un solo XML, agrupadas por prefijo (`ws-`, `qt-`, `ua-`, `qst-`, `panel-corners-`, `background-clock-`).
- **Módulos como features internas** — `QuickSettingsTweaksModule` crea sub-features (`QuickTogglesFeature`, `SystemItemsFeature`) dentro de su `enable()`.

* 4. Notas: lecciones y referencias

** Lecciones aprendidas

- **prefs.js vacío → crash**: `fillPreferencesWindow()` debe agregar al menos un widget. Si no, GNOME falla con "Extension did not provide any UI".
- **Import ESM sensible a mayúsculas**: `import {ModuleLoader}` debe coincidir exactamente con `export class ModuleLoader`.
- **Keybinding keys**: Deben coincidir exactamente entre el schema y `Main.wm.addKeybinding()`. Error → crash del Shell (retorno a GDM).
- **`hook.js`**: Siempre verificar `typeof originalMethod === 'function'` antes de parchear prototipos.
- **`Gtk.Switch` en GTK4**: Usar `'active'`, NO `'state'` (propiedad eliminada de GTK3). `settings.bind(key, sw, 'active', ...)`.
- **`_loadSettings()` reconectar handlers**: Si se usa señal `changed::`, desconectar viejos y reconectar al recargar settings. Nunca confiar en que la señal anterior sigue viva tras recarga.
- **Quick Text dual-process**: Diálogo modal en St/Clutter (dentro del Shell), ventana Actions en Gtk/Adw (proceso separado vía `Util.spawn()`). El subproceso necesita shebang `#!/usr/bin/gjs -m`.
- **Background Clock**: NO monkey-patchear `BackgroundManager.prototype._createBackgroundActor`. Usar `Main.layoutManager._backgroundGroup.add_child()`.
- **JS getters vs GObject properties**: No definir `get canPlay() { }` en una clase `GObject.registerClass` que ya declara `'can-play'` como `GObject.ParamSpec.boolean(READWRITE)`. El getter JS shadowea la propiedad GObject y como no tiene setter, `this.canPlay = value` lanza `TypeError: setting getter-only property`. La señal `notify::can-play` nunca se emite, rompiendo cualquier código que dependa de ella. Siempre verificar que no haya conflicto entre `Properties:` del `registerClass` y getters/setters del prototipo.

*** Lecciones de Overlay Mode (Quick Settings)

- El overlay (`QuickSettingsMenu._overlay`) necesita coordenadas stage-absolutas. Vincular constraints a `menu.box` da coordenadas relativas al padre → overlay aparece en x=0.
- Usar `menu._boxPointer` como source de `Clutter.BindConstraint` para ambos ejes (X e Y).
- `_xconstraint.offset` debe actualizarse en `_onOpen()` y en el handler `notify::height`, igual que `_yconstraint.offset`.
- Al fijar `menu.actor.width`, también setear `x_align = Clutter.ActorAlign.CENTER` para que el menú se centre dentro del overlay.
- Para animaciones con overshoot (flyout/dialog), usar `AdvAni.ease()` con `AdvAnimationMode.LowBackover` / `MiddleBackover` en vez de `Clutter.AnimationMode.EASE_OUT_BACK` / `EASE_OUT_EXPO`. Los custom bezier curves dan un efecto más natural.
- **Siempre conectar handlers GSettings ANTES del early return de `enabled`**, si no, al deshabilitar/re-habilitar el módulo nunca se vuelven a conectar las señales y el toggle queda muerto.
- Separar claves GSettings en dos grupos: las que requieren `disable()+enable()` (reload) y las que solo necesitan `_loadSettings()` (live: duration, style, overflow anchor).
- `_scheduleReload()` debe capturar `this._gsettings` en variable local antes de llamar a `disable()`, porque `disable()` lo setea a `null`. Sino `enable(this._gsettings)` recibe `null` y crashea.

*** Arte tras unlock: vfunc_paint → Clutter.Canvas

**Problema:** CSS `background-image` no funciona en ningún actor tras un lock/unlock de pantalla (GNOME Shell lo elimina del compositor y `set_style()` no puede restaurarlo, ni siquiera con data URIs).

**Solución:** Usar `Clutter.Canvas` como `this.content` del widget, dibujando el pixbuf con Cairo y clip circular (`cr.arc` + `cr.clip()` + `Gdk.cairo_set_source_pixbuf()` + `cr.paint()`). El Canvas siempre funciona, incluso tras unlock.

**Cambios en `crossfadeArt.js`:**
- Eliminado `vfunc_paint()`.
- Agregado `_initCanvas()`: crea `Clutter.Canvas`, conecta señal `draw` con renderizado Cairo circular.
- Agregado `_loadPixbufForCanvas()`: carga pixbuf desde `_currentUrl`, invalida canvas. Se llama desde `setArt()` (siempre) y `refreshStyle()`.
- `setArt()` ahora actualiza el Canvas además de crear capas CSS. Las capas CSS dan animación cruzada hasta el primer lock/unlock; después son transparentes y el Canvas es la fuente visible.
- `refreshStyle()` simplificado: destruye hijos, llama a `_loadPixbufForCanvas()`. No más `queue_repaint()`.
- **CRÍTICO:** `vfunc_get_preferred_width/height` deben mantenerse — sin ellos el widget reporta tamaño 0 y rompe el layout del dateMenu completo.

**Cambios en `mediaManager.js`:**
- Agregado `_lastKnownCover` (almacenado en cada cache hit/success de `getArtUrl()`)
- Agregado `getLastKnownCover()` — expuesto para unlock handler

**Cambios en `dateMenu.js`:**
- Handler `screen-unlocked` con tres capas de defensa:
  1. Meta D-Bus directa → `getArtUrl()` → `refreshStyle()`
  2. Fallback `getLastKnownCover()` si meta es null
  3. (implícito) `setArt()` en `media-changed` posterior actualiza Canvas

**Flujo post-unlock:**
1. Se obtiene el player activo y su metadata.
2. Si hay cover URL → se setea `_mediaArt._currentUrl` y se llama `refreshStyle()`.
3. `refreshStyle()` destruye capas CSS, carga pixbuf, invalida Canvas.
4. El Canvas dibuja el pixbuf con clip circular → el usuario ve el arte correctamente.
5. Si el módulo fue deshabilitado/re-habilitado durante el lock, `getLastKnownCover()` restaura la URL.

**Actualizaciones de media tras unlock:** Cuando cambia la canción después del unlock, `setArt()` es llamado por los signals normales (`media-changed`). Este actualiza el Canvas via `_loadPixbufForCanvas()`, y las capas CSS (transparentes post-unlock) se crean pero no afectan la visualización.

** Implementation strategy for step 1.5 (date menu media widget)

The widget should be injected into the date menu's **right column** (above the calendar grid) using the same pattern as userAvatarDateMenu:

1. **Module location**: `extension/modules/dateMenuMedia/` (separate from dateMenu module)
2. **Injection**: navigate to `_menuBox.get_last_child()` (right column), insert at index 0
3. **MPRIS data**: use existing `MediaPlayerManager` singleton from `utils/mediaPlayer/mediaManager.js`
4. **Cover art**: use `CrossfadeArt` from `dateMenu/crossfadeArt.js` (canvas-based for unlock safety)
5. **Widget structure**:
   - Base container: `St.BoxLayout` (vertical)
   - Album art area (if enabled)
   - Title + artist labels
   - Control buttons: prev, play/pause, next
   - Progress bar (optional, from QST)
6. **Settings prefix**: `dmm-` (Date Menu Media) to avoid conflict with dateMenu's `dm-*`
7. **Key settings for phase 1** (minimal):
   - `dmm-enabled` (bool) — master toggle
   - `dmm-show-prev`, `dmm-show-pause`, `dmm-show-next` (bools)
   - `dmm-control-opacity` (int, 0-255)
   - `dmm-compact` (bool)
   - `dmm-progress-enabled` (bool)
   - `dmm-progress-style` (string: 'slim'/'default')
8. **Layout styles from 1.6** (later):

   - `dmm-cover-width`, `dmm-cover-height`, `dmm-cover-roundness` (ints)
